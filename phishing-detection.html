ML / Detection CF-02

AI/ML Phishing Detection System

A hybrid URL-risk engine — a Random Forest classifier combined with rule-based signals — trained on 446,176 labeled URLs and evaluated on a held-out test set, including the cases it got wrong.

Overview

Most phishing links look wrong before you even load the page — a mismatched domain, a suspicious TLD, an unfamiliar structure. This project tests whether that intuition can be captured in a lightweight, fast, URL-only classifier: no page content, no network calls at request time, just the URL string itself. It's built as a full Flask application, not just a notebook — a scan endpoint, a login-gated admin dashboard, request history logging with live analytics, and CSV/PDF export of past scans.

Approach

Features

Each URL is reduced to 13 hand-engineered features before it ever reaches the model:

  • URL length, dot count, slash count, hyphen count
  • Presence of an @ symbol
  • Protocol used — HTTPS, HTTP, or none at all
  • Raw IP address in place of a domain name
  • Match against a whitelist of 22 commonly trusted domains
  • Subdomain depth
  • Match against a list of 15 TLDs disproportionately used for phishing (.xyz, .tk, .click, etc.)
  • A keyword-pressure score — count of terms like "login," "verify," "secure," and "bank" appearing in the URL

Model

A Random Forest classifier (150 trees, scikit-learn defaults otherwise) predicts a phishing probability from those 13 features. Random Forest was chosen over a single decision tree or logistic regression because URL-based signals interact non-linearly — a hyphen alone means nothing, a hyphen plus a suspicious TLD plus a missing HTTPS means a lot — and an ensemble of trees handles those interactions without needing them hand-specified.

Critically, the model's output isn't used directly as the final verdict. It feeds into a hybrid scoring formula:

risk_score = 0.6 × (model probability × 100) + 25 × (IP-in-URL flag) + 10 × (keyword pressure)

capped at 100, labeled PHISHING above a score of 50.

The reasoning: a raw ML score can be wrong with total confidence. Blending in two hard, auditable rule-based signals — a raw IP address standing in for a domain, and keyword pressure — means an obviously suspicious URL can't be waved through purely because the model's training data didn't cover it. A WHOIS domain-age lookup was scoped in as a fourth signal but deliberately left out of this version for latency and reliability — it's noted in the code as a safe future addition, not an oversight.

What the model actually leans on

Feature importance turned up something worth being upfront about: the model relies almost entirely on structural URL shape — whether a protocol is present, slash count, HTTP vs HTTPS, dot count, and URL length together account for over 85% of its decision weight. The two features that sound the most "clever" — trusted-domain whitelist match and suspicious-TLD match — barely move the needle (under 1% combined). The model learned that how a URL is put together predicts risk better than any specific list of good or bad domains.

Case Study: What It Caught

https://secure.runescape.rs-rr.xyz/pages/runescape/auth.php?id=748578

Flagged with a phishing probability of 1.0. This is a textbook lookalike: it borrows "runescape" in the subdomain to look legitimate at a glance, but the actual registered domain is rs-rr.xyz — a suspicious TLD, sitting behind a keyword ("secure") and an auth-flow path designed to look like a login page. Every signal pointed the same direction, and the model caught it with full confidence.

Case Study: What It Missed

https://baprov-visahome.com/aditionalinfo.php?accountid=...

Scored 0.38 — below the 0.5 threshold, so it was let through. This is a credential-harvesting page, but structurally it looks clean: valid HTTPS, a plausible-sounding (if slightly odd) domain, no IP address, no flagged TLD, low subdomain depth. The only tell is a misspelled path (aditionalinfo.php) and an accountid parameter — neither of which the current 13 features capture. This is the model's real limitation: it evaluates URL shape, not URL meaning, so a well-registered domain with a boring structure can carry a scam page straight past it.

Limitations & Next Steps

Two limitations are worth naming directly rather than glossing over. First, the case above: features derived purely from URL structure miss semantically deceptive but structurally clean phishing pages — closing that gap would mean adding page-content or domain-age signals (the WHOIS lookup mentioned above is the natural next step), not just more URL features. Second, working through the false negatives surfaced label noise in the training data itself — a portion of "phishing" negatives the model missed turned out to be ordinary sites (established institutional and corporate domains) mislabeled in the source dataset, not real detection failures. That's a dataset quality issue rather than a model issue, but it means the true real-world false-negative rate is likely somewhat better than the reported 7.6% suggests, and it's a reminder to audit training labels before trusting metrics at face value.

Beyond that: adversarial testing against newly registered or intentionally obfuscated domains, a retraining cadence as phishing tactics shift, and a human-review queue for borderline scores (35–65) rather than a hard 50-point cutoff.
