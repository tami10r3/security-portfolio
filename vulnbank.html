Offensive Security CF-01

VulnBank — External Web App Penetration Testing Report

A black-box security assessment of VulnBank's external web application, testing authentication, authorization, and API security controls. Scope was limited to the web application layer — network and mobile were not tested in this engagement.

Executive Summary

This assessment identified 15 vulnerabilities in VulnBank's web application, including 7 rated Critical. Overall risk is rated Critical: an attacker could bypass login entirely via SQL injection, view or modify any other user's financial data through broken authorization, and self-grant admin privileges during account registration — three independent paths to full account or system compromise, any one of which is sufficient on its own.

The application also failed to isolate its cloud environment from user input: a server-side request forgery flaw let an external request reach AWS's internal metadata endpoint, a class of bug that has led to major real-world breaches when left unpatched.

Methodology

Scope was limited to VulnBank's external web application — authentication, transaction, registration, and profile-management endpoints. Network infrastructure and the mobile application were explicitly out of scope for this engagement.

Testing followed a black-box approach: mapping the application's attack surface with two independently authenticated test accounts, then manually probing authentication, authorization, and business-logic flows. Burp Suite (Repeater and Intruder) was used for request interception, payload injection, and automated brute-force testing; jwt.io was used to decode and inspect session tokens for sensitive data exposure.

Findings

The 6 findings below represent the most distinct vulnerability classes identified. The remaining 9 are summarized in the table further down.

SQL Injection BOLA SSRF Mass Assignment BFLA JWT Exposure Other findings ↓
Critical

SQL Injection via Login Endpoint

Description
The login form at POST /login passes user input unsanitized into the backend database query, allowing SQL syntax to alter query logic.
Evidence
Submitting the payload ' OR 1=1-- in the username field returned an unexpected dataset instead of an authentication error, confirming the input reaches the query unescaped and exposing the underlying query structure.
Impact
An attacker can bypass authentication entirely, and depending on database permissions, read, modify, or delete records — potentially gaining full control of the backend.
Remediation
Replace dynamically constructed queries with parameterized queries or prepared statements; validate input type, format, and length server-side; deploy a WAF as a secondary control.
Critical

Unauthorized Access to Other Users' Data (BOLA)

Description
The transaction history endpoint does not verify that the requesting user owns the account they're querying.
Evidence
With two authenticated test accounts, submitting the second account's number on GET /transactions/{account_number} returned that user's full transaction history under the first user's session. Swapping JWTs between accounts produced the same result.
Impact
Any authenticated user can view — and potentially modify or delete — the financial data of any other user in the system.
Remediation
Add server-side authorization checks confirming the authenticated user's identity matches the requested resource before returning any data; deny mismatched requests outright.
Critical

Server-Side Request Forgery via User-Supplied URL

Description
The profile-picture-by-URL feature fetches whatever URL a user submits, without restricting the destination.
Evidence
Submitting http://169.254.169.254/ — AWS's internal instance metadata address — as the image URL on POST /upload_profile_picture_url caused the server to fetch it and return the metadata content directly in the response.
Impact
An attacker can pivot through the server to reach internal services and cloud metadata, potentially exfiltrating credentials and infrastructure configuration.
Remediation
Validate and allowlist permitted destination domains; explicitly block internal/private IP ranges (169.254.x.x, 10.x.x.x, 172.16–31.x.x, 192.168.x.x); route outbound fetches through a restrictive proxy.
Critical

Role Escalation via Mass Assignment (BOPLA)

Description
The registration endpoint accepts and processes fields beyond the intended input schema, including privilege-related fields.
Evidence
Adding "is_admin": true to the request body on POST /register caused the server to create the account with full administrative privileges.
Impact
Any unauthenticated user can self-grant admin access at signup, with no exploitation steps beyond submitting one extra field.
Remediation
Allowlist only expected fields on registration; assign roles exclusively server-side; reject requests containing unauthorized fields rather than silently ignoring them.
Critical

Privilege Escalation via Broken Function Level Authorization

Description
An administrative endpoint is reachable by any authenticated user, regardless of role.
Evidence
A standard test account was able to directly access /sup3r_s3cr3t_admin and reach admin functionality — the endpoint's obscurity was its only protection, not an actual authorization check.
Impact
Any authenticated user can reach administrative functions, risking confidentiality, integrity, and availability of the entire application.
Remediation
Enforce server-side role checks on every administrative route; never rely on hard-to-guess URLs as an access control mechanism; apply centralized role-based access control (RBAC).
Medium

JWT Token Exposes Sensitive Data

Description
The session token issued at login carries sensitive data in its payload rather than referencing it server-side.
Evidence
Decoding the JWT captured from GET /dashboard at jwt.io revealed passwords, internal user IDs, and role data stored in plaintext within the token itself.
Impact
Anyone who intercepts a token can extract credentials and role data directly, without needing to break any encryption — a direct path to account takeover and privilege escalation.
Remediation
Never place sensitive data in JWT payloads; use opaque tokens or encrypted claims where needed; enforce secure key management and rotation for token signing.

Other Findings

9 additional findings from the same assessment, summarized below.

FindingSeverityImpact, in short
Password Reset Abuse Critical No rate limit on password reset — 10-15 rapid requests all succeeded, enabling inbox flooding and OTP-guessing attacks.
CORS Allows Arbitrary Origins Critical API reflects and permits arbitrary origins, letting a malicious site make authenticated requests on a logged-in user's behalf.
No Account Lockout on Login High 31 failed login attempts via Burp Intruder, no lockout or HTTP 429 at any point — unlimited brute-force is possible.
No Rate Limiting on Auth Endpoints High Login and password reset both accept unlimited requests, enabling brute-force and credential stuffing.
Deprecated API Version Still Active High Downgrading a request from /api/v3/ to /api/v1/ reaches a live legacy endpoint returning excess data.
Username Enumeration via Error Messages Medium Distinct error messages for invalid usernames vs. wrong passwords let attackers build a list of valid accounts.
Missing Input Validation on Transaction Lookup Medium Malformed account numbers return HTTP 200 with an empty list instead of a proper error, aiding enumeration.
Weak Password Policy Medium No complexity or length requirements — passwords like "123" are accepted on registration and reset.
Missing HTTP Security Headers Medium No CSP, X-Frame-Options, X-Content-Type-Options, Referrer-Policy, or Permissions-Policy on any tested response.

Conclusion

VulnBank's current posture is Critical: three independent, low-effort paths (SQL injection, mass assignment, and BOLA) each lead to full compromise on their own, and the SSRF finding adds cloud infrastructure exposure on top. Fixing the 7 Critical findings — starting with input validation on the login and registration flows, and authorization checks on every object- and function-level request — would close off the most severe attack paths. The High and Medium findings compound risk (e.g. no account lockout makes the SQLi and enumeration findings easier to exploit at scale) and should be remediated as a second pass once the Criticals are resolved.

Note: VulnBank is a deliberately vulnerable application built for security training. All testing was performed in an isolated lab environment with no real user data involved.
